# Requirements Document

## Introduction

This specification defines the foundational database layer for the ArcPass sponsorship infrastructure. The scope is limited to initializing Prisma ORM with PostgreSQL in the existing pnpm monorepo, establishing a shared Prisma client package, defining the base schema structure for the four core entities (Wallet, SponsorshipRequest, RelayTransaction, RateLimit), and preparing the migration workflow. No sponsorship business logic or blockchain relay logic is implemented at this stage.

## Glossary

- **Prisma_Client_Package**: The shared package (`packages/shared`) that exports a configured Prisma client instance for consumption by `apps/api`, `apps/worker`, and other monorepo consumers.
- **Schema**: The Prisma schema file (`schema.prisma`) that defines database models, relations, enums, and the datasource configuration.
- **Migration**: A versioned SQL file generated by Prisma that applies schema changes to the PostgreSQL database.
- **DATABASE_URL**: An environment variable containing the PostgreSQL connection string used by Prisma at runtime and during migrations.
- **Datasource**: The Prisma configuration block that specifies the database provider and connection URL.
- **Generator**: The Prisma configuration block that specifies the client output target and generation settings.
- **Entity**: A database table represented as a Prisma model (Wallet, SponsorshipRequest, RelayTransaction, RateLimit).
- **Monorepo_Consumer**: Any app or package within the monorepo that imports and uses the shared Prisma client.

## Requirements

### Requirement 1: Prisma Initialization in Monorepo

**User Story:** As a developer, I want Prisma initialized within the monorepo's shared package, so that all apps can share a single schema and client configuration.

#### Acceptance Criteria

1. THE Prisma_Client_Package SHALL contain a `schema.prisma` file at `packages/shared/prisma/schema.prisma` that includes a `generator client` block targeting `prisma-client-js` and a `datasource db` block with provider set to `postgresql`.
2. THE Schema SHALL reference the `DATABASE_URL` environment variable using the Prisma `env()` function for the datasource connection string.
3. THE Prisma_Client_Package SHALL declare `@prisma/client` as a production dependency and `prisma` as a dev dependency in its `package.json`.
4. THE Prisma_Client_Package SHALL export a singleton Prisma client instance such that multiple imports from any Monorepo_Consumer resolve to the same client object within a single process.
5. WHEN a Monorepo_Consumer imports the Prisma client, THE Prisma_Client_Package SHALL provide a TypeScript-typed client exposing accessor properties for every model defined in `schema.prisma`.
6. THE Prisma_Client_Package SHALL include a `generate` script in its `package.json` that runs `prisma generate` and is registered as a dependency of the monorepo `build` pipeline so that the client is generated before any consuming app builds.
7. IF the `DATABASE_URL` environment variable is not set at the time of client instantiation, THEN THE Prisma_Client_Package SHALL throw an error indicating that the database connection string is missing.

### Requirement 2: Base Schema Structure

**User Story:** As a developer, I want the base schema to define the four core entities with their fields and relations, so that the database structure is ready for sponsorship logic implementation.

#### Acceptance Criteria

1. THE Schema SHALL define a Wallet model with fields: id (UUID primary key), walletAddress (unique, String, max 255 characters, stored as lowercase), firstSeenAt (DateTime, defaults to creation time), lastSeenAt (DateTime, defaults to creation time), sponsorshipCount (Int, default 0), isBlocked (Boolean, default false), and blockReason (optional String, max 500 characters).
2. THE Schema SHALL define a SponsorshipRequest model with fields: id (UUID primary key), walletId (FK to Wallet), status (enum: pending, approved, rejected, relayed, completed, failed, default pending), eligibilityReason (optional String, max 500 characters), requestedAt (DateTime, defaults to creation time), approvedAt (optional DateTime), rejectedAt (optional DateTime), completedAt (optional DateTime), failedAt (optional DateTime), ipAddress (optional String, max 45 characters), and userAgent (optional String, max 1024 characters).
3. THE Schema SHALL define a RelayTransaction model with fields: id (UUID primary key), sponsorshipRequestId (FK to SponsorshipRequest), transactionHash (unique, optional String, max 255 characters), status (enum: queued, submitted, confirmed, failed, default queued), relayAttempt (Int, default 1), submittedAt (optional DateTime), confirmedAt (optional DateTime), failedAt (optional DateTime), and failureReason (optional String, max 1000 characters).
4. THE Schema SHALL define a RateLimit model with fields: id (UUID primary key), identifier (String, max 255 characters), identifierType (enum: ip, wallet, user_agent), requestCount (Int, default 0), windowStart (DateTime, defaults to creation time), and blockedUntil (optional DateTime).
5. THE Schema SHALL define a one-to-many relation from Wallet to SponsorshipRequest where deleting a Wallet is restricted if associated SponsorshipRequests exist.
6. THE Schema SHALL define a one-to-many relation from SponsorshipRequest to RelayTransaction where deleting a SponsorshipRequest is restricted if associated RelayTransactions exist.
7. THE Schema SHALL define enums for SponsorshipRequestStatus (pending, approved, rejected, relayed, completed, failed), RelayTransactionStatus (queued, submitted, confirmed, failed), and RateLimitIdentifierType (ip, wallet, user_agent).
8. THE Schema SHALL enforce that the walletAddress field on the Wallet model is stored in normalized lowercase form regardless of input casing.
9. THE Schema SHALL create an index on the RateLimit model covering the identifier and identifierType fields to support efficient lookups during rate limit checks.

### Requirement 3: Migration Workflow

**User Story:** As a developer, I want a repeatable migration workflow, so that schema changes can be applied consistently across development and production environments.

#### Acceptance Criteria

1. THE Prisma_Client_Package SHALL include package.json scripts for generating migrations (`prisma migrate dev`), applying migrations (`prisma migrate deploy`), and generating the client (`prisma generate`).
2. WHEN a developer runs the migration generation script, THE Schema SHALL produce a timestamped SQL migration file in a `migrations` directory, where the migration directory name contains a numeric timestamp prefix and a descriptive name.
3. WHEN a developer runs the migration deploy script, THE Migration SHALL apply all pending migrations in sequential order to the target PostgreSQL database referenced by DATABASE_URL.
4. IF the DATABASE_URL environment variable is missing or contains an invalid connection string when a migration script is executed, THEN THE Migration SHALL exit with a non-zero exit code and an error message indicating the connection failure, without modifying the database.
5. IF a migration fails during deployment due to a conflict or SQL error, THEN THE Migration SHALL halt execution, roll back the failed migration, exit with a non-zero exit code, and report which migration file failed.
6. THE Prisma_Client_Package SHALL include a `.env.example` file containing a placeholder DATABASE_URL value that demonstrates the required PostgreSQL connection string structure including host, port, database name, username, and password placeholders.

### Requirement 4: Shared Client Strategy

**User Story:** As a developer, I want a single shared Prisma client module, so that all monorepo apps use the same database connection without duplicating configuration.

#### Acceptance Criteria

1. THE Prisma_Client_Package SHALL export a named `prisma` client instance from its package entry point defined in the package.json `exports` or `main` field.
2. THE Prisma_Client_Package SHALL implement a singleton pattern using `globalThis` to ensure that only one PrismaClient instance exists per process, including during development hot-reload scenarios where modules may be re-evaluated.
3. WHEN the apps/api package declares a workspace dependency on the Prisma_Client_Package, THE apps/api package SHALL be able to import the `prisma` instance and Prisma-generated types using the package name as the import specifier without referencing internal file paths.
4. WHEN the apps/worker package declares a workspace dependency on the Prisma_Client_Package, THE apps/worker package SHALL be able to import the `prisma` instance and Prisma-generated types using the package name as the import specifier without referencing internal file paths.
5. THE Prisma_Client_Package SHALL re-export all Prisma-generated model types and enums so that Monorepo_Consumers can use them for type safety without importing from `@prisma/client` directly.
6. IF the `DATABASE_URL` environment variable is not set when the Prisma client is instantiated, THEN THE Prisma_Client_Package SHALL throw an error indicating that the database connection string is missing.
7. WHEN a consumer runs the Prisma_Client_Package build or prepare step, THE Prisma_Client_Package SHALL execute `prisma generate` to ensure the generated client is available before the module can be imported.

### Requirement 5: Environment Configuration

**User Story:** As a developer, I want database configuration driven entirely by environment variables, so that no secrets are committed to source control and deployments remain flexible.

#### Acceptance Criteria

1. THE Schema SHALL use `env("DATABASE_URL")` as the datasource URL value.
2. THE Prisma_Client_Package SHALL not contain any hardcoded connection strings in any committed source file, configuration file, or generated output checked into version control.
3. THE Prisma_Client_Package SHALL include documentation (via `.env.example`) specifying the expected DATABASE_URL format: `postgresql://<user>:<password>@<host>:<port>/<database>?schema=public`.
4. IF the DATABASE_URL environment variable is not set or is an empty string, THEN THE Prisma_Client_Package SHALL throw an error at client instantiation time that includes the name of the missing variable ("DATABASE_URL") and the expected format.
5. THE Prisma_Client_Package SHALL include a `.gitignore` entry that excludes `.env` files (but not `.env.example`) from version control.

### Requirement 6: Monorepo Integration

**User Story:** As a developer, I want Prisma integrated cleanly into the existing pnpm workspace and Turborepo pipeline, so that builds and migrations work within the established tooling.

#### Acceptance Criteria

1. THE Prisma_Client_Package SHALL be registered in the pnpm workspace via the existing `pnpm-workspace.yaml` configuration (packages/* pattern).
2. THE Prisma_Client_Package SHALL include a `build` script that runs `prisma generate` to produce the client, with generated output placed in a directory matching the Turborepo `outputs` configuration (dist/**) for build caching.
3. WHEN Turborepo runs the `build` pipeline, THE Prisma_Client_Package SHALL generate the Prisma client before dependent packages build, as enforced by the existing `"dependsOn": ["^build"]` task topology.
4. THE Prisma_Client_Package SHALL provide a TypeScript entry module that re-exports the generated Prisma client, allowing dependent workspace packages to import the client using the pnpm workspace protocol (e.g., `"workspace:*"` dependency declaration).
5. IF `prisma generate` fails during the build pipeline, THEN THE Prisma_Client_Package build script SHALL exit with a non-zero exit code, causing the Turborepo pipeline to halt and report the failure.
